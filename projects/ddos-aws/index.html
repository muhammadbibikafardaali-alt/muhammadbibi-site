DDoS mitigation and log management on AWS

Keeping a webshop available while it is under attack, and making sure the logs can explain afterwards what happened.

01 · Problem

A webshop that goes down under attack loses orders, and nobody can say why.

A webshop on AWS needed protection against distributed denial-of-service (DDoS) attacks. Two kinds of attack matter: network floods (layer 3 and 4, such as SYN or UDP floods) that try to saturate the connection, and application floods (layer 7) that send large numbers of valid-looking HTTP requests to expensive pages like search or checkout.

Its logs were spread over several services, so after an incident there was no single place to see who sent what, what was blocked, and what reached the servers.

02 · Approach

Filter at the edge, collect every log in one place, automate the response.

Choosing the protection layer

Before building, I compared AWS-native protection with Cloudflare, on what each stops, where it sits, what it logs and what it costs.

Network floods (L3/L4)Shield Standard: automatic, free for every AWS account.Unmetered DDoS mitigation on every plan, including free.

CostWAF: $5 per web ACL and $1 per rule per month, plus $0.60 per million requests. Shield Advanced: from $3,000 a month, one-year commitment.Free tier available; paid plans per month.

The webshop already ran on AWS, so I built the AWS option: protection, logs and automation in one account, with Lambda able to change WAF rules directly.

Shield Standard or Shield Advanced?

Shield Standard already absorbs common network floods at no cost. Shield Advanced adds layer-7 detection, the Shield Response Team, cost protection against scaling charges during an attack, and WAF fees included for protected resources. At $3,000 a month with a one-year commitment, plus data transfer fees, it pays off for large sites that are attacked often, not for a small webshop. The design therefore uses Shield Standard with a well-tuned WAF, and keeps Advanced as the upgrade path.

What I built

  • Network. A VPC with the EC2 webshop instances in private subnets. Security groups allow web traffic only from the load balancer, so the servers cannot be reached directly.
  • Edge filtering. An AWS WAF web ACL on the load balancer with AWS managed rule groups (core rule set, known bad inputs, IP reputation list) and a rate-based rule that blocks any IP sending too many requests in a five-minute window.
  • Logging. WAF logs, VPC Flow Logs and CloudTrail collected in CloudWatch Logs, with CloudWatch Logs Insights queries to answer "who, what, when" after an incident.
  • Alerting. CloudWatch alarms on blocked-request and request-count metrics, so an attack is noticed while it happens.
  • Automated response. A Lambda function reads the logs, finds offending IPs and adds them to a WAF IP set that is blocked, closing the loop without manual work.
  • Infrastructure as code. Everything defined in Terraform, so the setup can be reviewed, rebuilt and torn down.

How I tested it

In a test environment I sent request bursts above the rate limit and requests matching known-bad patterns, then checked three things: WAF blocked them, the CloudWatch metrics and alarms showed the attack, and the Lambda function added the source to the block list.

03 · Result

Assessed Outstanding.

Final presentation on 8 February 2024, graded Outstanding by Fontys. The final design filters flood traffic at the edge before it reaches the servers, and every blocked request can be traced afterwards in one place.

04 · Lessons

What I would keep, and what I would do differently.

  1. L1

    Start with the free layer. Shield Standard plus tuned WAF rules covers most of what a small shop faces. Paying for Shield Advanced is a business decision about risk, not a default.

  2. L2

    Logs only help if they are in one place and you can query them. Collecting them is easy; deciding the questions you will ask during an incident is the real work.

  3. L3

    Following one request from the edge to the server and back through the logs is the same skill I now use every day on payment requests and webhooks.
